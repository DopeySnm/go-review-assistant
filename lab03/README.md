# Лаба 03. Чат-агент на LangChain: память диалога, свой компонент, развилки

Продолжение лабы 02 (`../lab02`): тот же наставник с памятью фактов, плюс память диалога buffer / summary,
свой компонент с инструментом и развилки — см. раздел «Доработка» ниже.

Наставник по Go-код-стайлу команды (тема семестрового проекта): знакомится с разработчиком, по одному задаёт
вопросы (имя, уровень, опыт, стек, проект, слабые места, цель), хранит **факты** в `memory.json` и после
перезапуска продолжает с тех, на которые ответа ещё нет. Когда всё известно — режим наставника: объясняет
правила S1–S6, проверяет код инструментом, задаёт вопросы квиза по уровню знаний (уровень и ошибки тоже хранятся
в `memory.json`), упрощает объяснение, если пользователь недоволен. История диалога в промпте — окно или окно
с резюме.

## Сдаётся

- `lab03.ipynb` — ноутбук с кодом и выводами двух сеансов: первый запуск → перезапуск ядра → второй сеанс,
  плюс ещё профили (`guest`, `dmitry`, `olga`), режим наставника (развилки, инструмент, квиз) и сравнение
  памяти диалога buffer / summary;
- `memory.json` — файл памяти после демонстрации.

`fact_agent.py` создаётся самим ноутбуком (`%%writefile`), чтобы после перезапуска ядра его можно было импортировать.

## Как устроено

| Требование | Где |
|---|---|
| Чат на LangChain | `CHAT_PROMPT \| ChatOpenAI` в `RunnableWithMessageHistory` (история — только в RAM сеанса) |
| Память — факты, а не история | `FileFactMemory(BaseChatMemory)`: `load_memory_variables()` / `save_context()` |
| Извлечение — отдельный LLM-вызов, JSON | `with_structured_output(..., method="json_schema")`, схема — Pydantic `UserFacts` |
| Файл есть — читаем, нет — пусто | `FileFactMemory.model_post_init` |
| Несколько профилей | ключ `user_id` в `memory.json` |
| Служебный вывод — в своей ячейке | `LogCell`: ячейка с `display_id`, агент обновляет её вывод |
| Не переспрашивать | следующий вопрос — первый недостающий факт; известные факты не перезаписываются |

## Доработка: память диалога, свой компонент, развилки

Когда факты собраны, агент — наставник. Каждая реплика проходит
`классификатор (LLM, JSON) → TurnParser → RunnableBranch`, всё это внутри `RunnableWithMessageHistory`.

| Требование | Где |
|---|---|
| Память: контекстное окно (buffer) | `DialogHistory(BaseChatMessageHistory)`, `dialog="buffer"`: в промпт — последние `window` сообщений (`trim_messages`, `token_counter=len`) |
| Память: суммаризация | `dialog="summary"`: выпавшие из окна сообщения отдельный LLM-вызов (`SUMMARY_PROMPT`) дописывает в резюме; резюме — в системный промпт, хвост — сообщениями |
| Свой компонент с разбором параметров | `TurnParser(Runnable)`: из реплики и ответа классификатора `Route` (`intent`, `rule`, `mood`) — параметры хода; явные признаки (блок кода, ожидается ответ квиза, номер правила, «не понял», повтор) важнее ответа модели |
| …с действием tool | `check_code` (`@tool`): линтер S1–S6 на регулярках, на коде лабы 1 находит все 8 нарушений без ложных; модель только объясняет его отчёт |
| …с элементом памяти в файле | `progress` в `memory.json`: уровень по квизу, серия ответов, ошибки по правилам (`FileFactMemory.save_progress`) |
| Развилка по классу вопроса | `RunnableBranch`: `explain_rule` / `review_code` / `quiz` / `quiz_answer` / `other` |
| Развилка по настойчивости / негативу | `simplify`: «не понял», «опять», «всё равно…» или повтор прошлой просьбы; упрощаем то, что объясняли; на второй ход подряд — предложить разобрать на своём коде |
| Уровень знаний в памяти → сложность | глубина объяснения (`DEPTH`) и вопросы квиза по уровню; два верных подряд — уровень выше, две ошибки — ниже; сначала правила с ошибками и слабое место |

## Запуск

```bash
pip install -r requirements.txt
llama-server -m qwen2.5-3b-instruct-q4_k_m.gguf -c 8192      # или OpenRouter: LLM_BASE_URL, LLM_MODEL, LLM_API_KEY
jupyter lab lab03.ipynb                                       # интерактивно: agent.chat()
python run_demo.py lab03.ipynb                                # выполнить целиком с настоящим перезапуском ядра
```

`run_demo.py` выполняет ячейки до «Перезапуск ядра» в одном ядре, остальные — в новом: в выводе другой pid
и нумерация ячеек с 1.

Вывод в ноутбуке получен на GPU Tesla T4 (llama-server + Qwen2.5-3B, `-ngl 99`) тем же `run_demo.py`.

## Что выяснилось про Qwen2.5-3B

Модель — та же, что в лабе 1. Структура JSON у неё всегда валидная: llama-server строит грамматику по схеме.
Ломалось содержимое, и чинилось кодом, а не промптом:

| Прогон | Проблема | Исправление |
|---|---|---|
| 1 | заполняет все поля из любой реплики и перезаписывает известное: имя `junior`, потом `NixOS`; `go_experience: "more_than_one_year"` | известные факты не перезаписываются; `accept_fact` — факт должен быть в реплике (имя — в тексте, уровень — `junior/middle/senior` или «джун/мидл/сеньор», опыт — число или «год/лет/месяц»), стек, проект, слабые места и цель — только в ответ на свой вопрос |
| 1 | вместо «какой у тебя уровень» спрашивает «Знаешь ли ты обработку ошибок?» | модель получает вопрос дословно |
| 2 | раскладывает ответ по уже известным полям («с PostgreSQL и Docker» → `go_experience`) | в схеме только недостающие поля |
| 3 | раскладывает перечисление по полям: `stack: PostgreSQL`, `project: Docker`, `weak_spots: NixOS` | в схеме только поле, о котором спросили, и короткие факты (имя, уровень, опыт), которые называют попутно |
| 4 | — | все 7 фактов верные, ничего не переспрашивает |
| 5 | добавлены профили `dmitry`, `olga` и возвращение `guest`: на «Биллинг: считаем платежи…» модель вернула `project: null`, агент четыре раза переспросил проект | спрошенное поле в схеме — обязательная строка с выходом «нет» (необязательное модель охотно оставляет null) |
| 6 | — | у `artur`, `dmitry`, `guest` все 7 фактов, у `olga` 4 (ушла после стека), ничего не переспрашивает |

Не исправлено: иногда вставляет китайское слово («код-стайл顾问»), несмотря на запрет в промпте; примеры кода
в режиме наставника простые и не всегда про слабое место пользователя.

## Что выяснилось в доработке

Три прогона на Kaggle (Qwen2.5-3B), каждый раз весь ноутбук. Как и с фактами, чинилось в основном кодом:

| Прогон | Проблема | Исправление |
|---|---|---|
| 1 | классификатор на «Объясни правило S3», «А что с правилом S2?» отвечает `review_code`; ветка проверки получает пустой код, модель сочиняет правило (S5 «про комментарии») | `TurnParser`: без кода проверки нет, номер правила в реплике → `explain_rule`; без правила и слов «объясни/покажи» → `other` |
| 1 | `mood: недоволен` почти на каждую реплику (14 из 17) | поле убрано; недовольство — по словам («не понял», «всё равно», «опять») и повтору прошлой просьбы |
| 1 | резюме из одного приветствия — выдуманный диалог; дальше модель копирует реплики вместо пересказа и, переписывая резюме целиком, теряет старое («Сергей» пропал через ход) | приветствие не сворачиваем; резюме — список пунктов, каждый кусок пересказывается отдельно; код вырезается |
| 1 | после вердикта квиза (код) модель ему противоречит: «Неверно: S5. Верно: S2…», «Верно… S6 не нарушено» | объяснение ответа — поле `why` в банке вопросов, без LLM |
| 1 | из отчёта `check_code` (S1, S4, S5) модель упомянула только S4 | отчёт вставляется в ответ дословно, модель только объясняет и исправляет |
| 2 | пункты резюме — всё ещё копии реплик вместе с объяснениями наставника; на «Кто делает ревью?» — «Дмитрий» | в пересказ идут реплики пользователя и обрезанные (150 символов) ответы наставника; пункт — одно предложение «Пользователь …» |
| 2 | «Какая сегодня погода?» → «укажите ваш город, я найду» | ветка «другое»: «на такие вопросы не отвечаешь и уточнений не просишь» |
| 3 | — | buffer: на «Кто у нас делает ревью?» — общие слова; summary: «выполняет Сергей, придирается к именованию». Квиз junior → middle, упрощение объясняет S5 против S2, погода — отказ и возврат к теме |

Не исправлено:

- объяснения правил иногда неверны: при окне в 4 сообщения модель копирует структуру прошлого ответа и
  объясняет S3 как «context.Context» или S2 как «defer x.Close() — плохо», хотя текст правила есть в промпте;
- в упрощении может перепутать формулировку («S2 предписывает не проверять ошибки»), пример кода — не всегда по правилам;
- классификатор почти бесполезен: класс в итоге определяют признаки в `TurnParser`; модель нужна только
  для реплик без явных признаков;
- извлечение фактов недетерминировано и между прогонами: в одном прогоне «джун» извлечено как `middle`
  (отброшено проверкой, у `olga` остались 2 факта), в другом слабое место записано по-китайски.

Прогон ноутбука на T4 — около 2,5 минуты.

Версии: langchain-core 1.6.9, langchain-openai 1.7.0, langchain-classic 1.0.8.

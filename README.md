# Задание 01. Развёртывание LLM и ассистент с вызовом функций

> Задание 02 (чат-агент на LangChain с памятью фактов) — в папке [`lab02/`](lab02/README.md).

**Тема проекта:** проверка Go-кода по код-стайлу команды.
Ассистент получает правила (`get_style_guide`), код (`get_code(file)`) и отчёт линтера (`get_linter_report`) и находит нарушения.

Машина: Intel Core i5-3570K (4 ядра, без AVX2), 16 ГБ RAM, NixOS. llama.cpp b6981 из nixpkgs (`nix-shell` → `llama-server`, `llama-bench`).
Прогоны агента — на Kaggle (Tesla T4), та же версия llama.cpp, собранная с CUDA (`kaggle/`).

## Развёртывание LLM

1. **maple-preview на CPU** — файл модели не получен, замер сделан на моделях из домашнего задания (п. 1 ниже).

2. **GPU** — локальной видеокарты нет. На Kaggle T4 те же модели дают 80–110 ток/с генерации (поле `timings` в логах), то есть в 40–50 раз быстрее моего CPU.

3. **OpenRouter: сравнение с локальной моделью**

   ```bash
   export LLM_API_KEY=$(cat .openrouter_key)

   curl -s http://127.0.0.1:8080/v1/chat/completions \
     -H "Content-Type: application/json" \
     -d '{"messages": [{"role": "user", "content": "Сколько букв r в слове strawberry?"}]}' \
     | jq '{model, content: .choices[0].message.content}'
   ```

   Output (Qwen2.5-3B, локально):
   ```json
   {"model": "gpt-3.5-turbo", "content": "В слове \"strawberry\" входит 4 буквы \"r\"."}
   ```

   ```bash
   curl -s https://openrouter.ai/api/v1/chat/completions \
     -H "Authorization: Bearer $LLM_API_KEY" \
     -H "Content-Type: application/json" \
     -d '{"model": "nvidia/nemotron-3-super-120b-a12b:free", "messages": [{"role": "user", "content": "Сколько букв r в слове strawberry?"}]}' \
     | jq '{model, content: .choices[0].message.content}'
   ```

   Output:
   ```json
   {"model": "nvidia/nemotron-3-super-120b-a12b:free", "content": "В слове **strawberry** три буквы **r**."}
   ```

   Локальная 3B ошибается (4), облачная 120B отвечает верно (3).

### 4. Ассистент с вызовом функций (tools)

```bash
python hw01.py --prompt v9            # REPL-агент
python hw01.py --prompt v9 --batch    # 10 тестовых вопросов, лог в logs/
```

- Функции захардкожены: правила S1–S6, два Go-файла (`handler.go`, `repo.go`) с 8 заложенными нарушениями, отчёт линтера, который находит только 3 из 8.
- Вызов — строка `CALL get_code {"file": "handler.go"}` в тексте ответа. Парсер терпим к `get_code("handler.go")`, `call:`, ключам `"filename"`, `"файл"`; несколько вызовов в одном сообщении выполняются по очереди; повторный одинаковый вызов не выполняется.
- Результат возвращается модели сообщением `РЕЗУЛЬТАТ get_code(...)`. Это же слово — стоп-последовательность, а текст после последнего `CALL` отрезается: маленькие модели любят дописывать выдуманный результат.
- Лимит 6 шагов на вопрос и `max_tokens: 800` против зацикливания.

### 4.1. Прогон на 2 LLM + логи

Вопросы, одинаковые для обеих моделей:

1. Проверь handler.go.
2. Есть ли в коде имена не в camelCase?
3. Где проигнорированы ошибки? (ловушка: `_, err :=` — не игнорирование)
4. Можно ли вызывать panic в обработчике? Есть ли такое у нас?
5. Все ли функции работы с БД принимают context?
6. Правильно ли оборачиваются ошибки в repo.go?
7. Проверь метод ListOrders в handler.go. (нарушений нет)
8. Что нашёл линтер? Он нашёл всё?
9. Проверь файл main.go. (файла нет)
10. Сколько всего нарушений и какое правило нарушено чаще всего?

```bash
kaggle/run.sh qwen:v1 llama:v1
```

Логи: `logs/qwen2.5-3b-instruct-q4_k_m_v1.log`, `logs/Llama-3.2-3B-Instruct-Q4_K_M_v1.log`.

Qwen вызывает `get_code`, но стайлгайд открыла в 1 вопросе из 10 и судит по своим представлениям: «код соответствует код-стайлу», panic «соответствует правилам, но может быть нежелательным», `return err` без обёртки — «корректно». На вопросы про ошибки и про количество нарушений пересказывает отчёт линтера и считает, что он полный.
Llama чаще вызывает не ту функцию (`get_style_guide {"аргумент": "repo.go"}` вместо кода), после ошибки «файл не найден» сама переключается на handler.go, на вопрос про main.go выдумала «правила» («РULE 1. В файле main.go не должно быть импортов») и зациклилась на них.
Обе модели: 0 из 19 эталонных нарушений названы с файлом и строкой.

Для сравнения — облачная Nemotron-3-Super-120B с промптом v4 (`logs/nvidia_nemotron-3-super-120b-a12b_free_v4.log`): верно 6 из 10, 14 из 19 нарушений. Её прогон выявил неоднозначность в моих данных: по правилу S4 HTTP-обработчик тоже «ходит в БД» и должен принимать ctx. В S4 добавлено «HTTP-обработчики берут контекст из r.Context()».

### 4.2. Prompt engineering до 4B

Модель — Qwen2.5-3B, вопросы из п. 4.1, temperature 0.1. Промпты — `PROMPT_V1`–`PROMPT_V9` в `hw01.py`. v1–v3 — один прогон, v4–v9 — три.

```bash
kaggle/run.sh qwen:v2 qwen:v3 qwen:v4:3 qwen:v5:3 qwen:v6:3 qwen:v7:3 qwen:v8:3 qwen:v9:3
python score.py logs/qwen*.log
```

`score.py` достаёт из финального ответа все `файл:строка` и сравнивает с эталоном: «верно» — ответ полностью совпал с эталоном, «найдено» — сколько эталонных нарушений названо, «ложных» — названные места, которых нет в эталоне, «нужные вызовы» — вызваны все нужные функции и файлы.

| Промпт | Что изменено | Нужные вызовы | Верно | Найдено | Ложных | Результат |
|---|---|---|---|---|---|---|
| v1 | роль, функции, формат вызова | 7/10 | 1/10 | 0/19 | 0 | стайлгайд не открывает, «всё соответствует» |
| v2 | шаги, правила, пример диалога | 8/10 | 2/10 | 0/19 | 2 | пересказывает правила, на вопросе 10 зацикливается на примере |
| v3 | запрет писать результат, «линтер находит не всё», формат строки, «если нет — Нарушений нет» | 8/10 | 1/10 | 0/19 | 0 | на все 10 вопросов «Нарушений нет» |
| v4 | примеры «Ответ 1/2/3» с вызовами, подсказки как искать каждое правило, «проверь КАЖДОЕ правило» | 21/30 | 5/30 | 14/57 | 117 | вызовы стабильны, но по строке на каждое правило; из примера протекает `store.go`; линтер не вызывает |

| v8 | примеры показывают все вызовы одним сообщением и проверку нескольких правил | **30/30** | 6/30 | 9/57 | 22 | вызовы идеальны; половина ответов пустые — см. ниже |

**Что получилось.** Вызов инструментов маленькая модель освоила: с v8 Qwen в каждом вопросе открывает стайлгайд и нужные файлы, при отсутствии файла в вопросе — оба файла, на вопрос про линтер — линтер, на main.go честно отвечает «файл не найден». Решающим оказался пример диалога, где вызовы показаны, а не описаны: текстовые инструкции и ветвления (v5, v6) модель не выполняет.

**Что не получилось.** Читать код Qwen-3B не умеет: при «проверь все правила» пишет строку почти на каждое правило (v4, v9 — около 100 ложных срабатываний на 30 вопросов), при узких промптах находит мало. Лучшее, что удалось: 26 из 57 нарушений (v9), при этом номера строк часто сдвинуты на 1–3, `if err != nil {` принимается за проигнорированную ошибку, `return &u, nil` — за необёрнутую. Подсчёт «сколько всего нарушений» (вопрос 10) и сравнение с линтером (вопрос 8) не получились ни в одной версии.

**Наблюдения про маленькие модели:**
- готовые фразы в промпте («Нарушений нет», «Файл не найден») становятся ответом по умолчанию (v3, v6);
- модель копирует примеры буквально: имя файла `store.go` (v4), «Правило S3» (v7), подпись «Ассистент после РЕЗУЛЬТАТ:» (v8 — модель начала ответ словом «РЕЗУЛЬТАТ», клиент оборвал генерацию на стоп-последовательности, половина ответов пустые);
- пример, совпадающий с тестовым вопросом, — это утечка ответа: в v8 пример «Есть ли panic в коде?» → `handler.go:22` совпал с вопросом 4, поэтому v8 на этом вопросе не учитывается.

**Ограничения оценки.** `score.py` учитывает только упоминания `файл:строка`, поэтому для v1–v3, которые отвечают без номеров строк, «найдено» = 0 даже при частично верном тексте. Правило S4 уточнено до всех прогонов Qwen и Llama, но после прогона Nemotron. Правило S2 уточнено («`defer x.Close()` допускается») перед v5.

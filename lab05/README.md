# Лаба 05. RAG в цикле вопросов-ответов

Наставник по Go-код-стайлу из лаб 2–3 (память фактов, память диалога, развилки, инструмент `check_code`)
отвечает на вопросы о стиле Go **по базе знаний** — руководствам, а не по памяти модели, и ссылается на источники.

## Сдаётся

- `lab05.ipynb` — ноутбук с кодом и выводами: база знаний, качество поиска, порог, модель без базы и с базой,
  перезапуск ядра (индекс читается с диска), наставник с RAG;
- `kb/` — база знаний; `memory.json` — профиль после демонстрации.

`kb.py` и `fact_agent.py` создаются самим ноутбуком (`%%writefile`).

## Как устроено

| Требование | Где |
|---|---|
| Документы | `kb/team_style.md` — правила S1–S6 с объяснением и примерами (по-русски, свой текст); `kb/code_review_comments.md`, `kb/effective_go.md`, `kb/uber_style.md` — снимок открытых руководств (`fetch_kb.py`, ссылки и лицензии — `kb/sources.json`) |
| Разбиение | `kb.load_chunks`: `MarkdownHeaderTextSplitter` по заголовкам → `RecursiveCharacterTextSplitter` до 1200 символов; к тексту — «Источник. Раздел»; оглавления отброшены |
| Эмбеддинги | bge-m3 Q8_0 в llama-server `--embeddings --pooling cls`, через `OpenAIEmbeddings(check_embedding_ctx_length=False)`; мультиязычная: вопрос по-русски находит английский раздел |
| Векторное хранилище | `InMemoryVectorStore`, косинусная близость; `dump`/`load` в `kb_index.json`, пересчёт только при изменении чанков (хэш в `kb_index.meta.json`) |
| RAG-цепочка | `kb.make_rag_chain`: вопрос → `search` → `format_context` → `RAG_PROMPT` → модель → список источников (пишет код) |
| RAG в цикле вопросов-ответов | `FactAgent(kb=...)`: `классификатор → TurnParser → _retrieve → RunnableBranch`; ветки «объяснить правило» и «вопрос по базе знаний» получают фрагменты в промпт, отвечают со ссылками [1], [2] |
| Развилка по релевантности | `_retrieve`: близость лучшего фрагмента ≥ порога — ветка «вопрос», иначе «другое» (не по теме, разговор); порог — `KnowledgeBase.calibrate()` |
| Оценка | `kb.EVAL` — 14 вопросов с известными разделами-ответами: hit@1, hit@4, MRR; `OFF_TOPIC` — вопросы не по теме для порога |

## Запуск

```bash
pip install -r requirements.txt
llama-server -m qwen2.5-3b-instruct-q4_k_m.gguf -c 8192 --port 8080
llama-server -m bge-m3-Q8_0.gguf --embeddings --pooling cls -c 8192 -b 8192 -ub 8192 --port 8081
jupyter lab lab05.ipynb
python run_demo.py lab05.ipynb       # выполнить целиком с настоящим перезапуском ядра
python fetch_kb.py                   # обновить снимок руководств в kb/
```

bge-m3 GGUF — `https://huggingface.co/gpustack/bge-m3-GGUF` (`bge-m3-Q8_0.gguf`, 635 МБ).

Вывод в ноутбуке получен на GPU Tesla T4 (два llama-server с `-ngl 99`) тем же `run_demo.py`.

## Результаты (Kaggle T4, Qwen2.5-3B + bge-m3)

База знаний: 267 чанков (Code Review Comments — 41, Effective Go — 119, Uber — 100, командный — 7),
индекс строится за 11 с, после перезапуска ядра читается с диска.

**Поиск** на 14 вопросах по-русски: hit@1 = 0,86, hit@4 = 1,00, MRR = 0,93. Два промаха на первом месте —
«пустой срез» (первым нашёлся соседний раздел Uber про `var` для нулевых структур) и «именованные результаты»
(первым — тот же раздел из Effective Go, а не Code Review Comments). Вопрос по-русски находит английский
раздел: «Как называть ресивер метода?» → Receiver Names, близость 0,56.

**Порог**: вопросы по теме — близость 0,534…0,677, не по теме — 0,309…0,452; порог 0,493 разделяет без ошибок.

**Модель без базы и с базой** (одни и те же вопросы):

| Вопрос | Без базы | С базой |
|---|---|---|
| Как называть ресивер метода? | «называют сигнатурой метода» / «по имени типа: `Person`» | коротко, 1–2 буквы: `c`, `cl` для `Client`; не `this`/`self` [1] |
| С какой буквы текст ошибки, нужна ли точка? | «с маленькой буквы и заканчивается точкой» | со строчной, без точки в конце [1] |
| Где объявлять интерфейс? | «рядом с реализацией» | в пакете, который его использует [1] |

Без базы модель ошибается во всех трёх, с базой — отвечает по руководству.

**Наставник с RAG**: вопросы про получателя метода и про `context.Context` в структуре ушли в ветку «вопрос по базе
знаний», «Объясни правило S5» — в «объяснить» с командным текстом и Uber Error Wrapping, погода — ниже порога
(0,45), квиз и ответ на него — как в лабе 3.

## Что выяснилось

| Прогон | Проблема | Исправление |
|---|---|---|
| 1–3 | llama-server на Kaggle не стартует: `libcudart.so.12: cannot open shared object file` — в новом образе CUDA 13, а сервер собран ноутбуком `hw01-llama-build`, закреплённым за старым образом | скрипт запуска на Kaggle: если сервер не запускается, ставит `nvidia-cuda-runtime-cu12`, `nvidia-cublas-cu12` из pip и добавляет их в `LD_LIBRARY_PATH` |
| 4 | модель дописывает свой список «Источники:» по образцу прошлых ответов из истории — с выдуманными пунктами | список модели обрезается (`strip_sources`), остаётся список, который пишет код |
| 4 | соседние чанки одного раздела — два одинаковых источника («Error Wrapping» дважды) | `group_hits`: чанки одного раздела — один фрагмент |
| 5 | классификатор отнёс вопрос про имя получателя к квизу; следующую реплику «Объясни правило S5» парсер принял за ответ на квиз (в ней «S5») | квиз — только по просьбе; ответ на квиз — реплика до 4 слов без «объясни/покажи» |
| 6 | на вопросе про `context.Context` модель зациклилась («Правило S1…S47…») на 80 с | `langchain-openai` 1.7 шлёт лимит как `max_completion_tokens`, llama-server b6981 его не знает — лимит не работал и в лабах 2–3; `make_llm` дублирует `max_tokens` в `extra_body` |
| 7 | — | все ветки верные, ответы с источниками, ноутбук — 52 с |

Не исправлено:

- уточняющий вопрос без контекста («А можно назвать его self?») проходит порог еле-еле (0,51 при 0,493):
  в нём самом нет слов про ресивер. Лечится переформулировкой запроса с учётом истории
  (history-aware retriever), но для 3B это ещё один ненадёжный вызов;
- порог откалиброван на тех же вопросах, на которых измерен поиск; на новых вопросах ошибки возможны;
- на вопрос не по теме модель отвечает «нет доступа к погоде, посмотри на сайтах», а не возвращает к теме,
  хотя развилка сработала верно;
- ответы иногда длиннее, чем просит промпт (3–5 предложений), и повторяют пример дважды.

Локально на NixOS numpy (нужен `InMemoryVectorStore`) не находит `libstdc++.so.6`:
`LD_LIBRARY_PATH=$(nix-build '<nixpkgs>' -A stdenv.cc.cc.lib --no-out-link)/lib`.

Версии: langchain-core 1.6.9, langchain-openai 1.7.0, langchain-text-splitters 1.1.3, llama.cpp b6981.
